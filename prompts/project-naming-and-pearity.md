# Structured Project Names + Pearity Tag Integration (Utility side)

## Part A: Structured project names

### Goal

New projects are named from four fields instead of free text, so names are consistent:

**`Brand_Type_MonYYYY_Name`**, for example `Wasl_Campaign_Oct2026_JGE Launch`.

| Field | Input | Rules |
|---|---|---|
| **Brand** | Brand picker (existing brands; admins can add one inline) | required |
| **Type** | Campaign · Program · Project | required. Admins can manage this list in Settings → Projects. |
| **Month** | Month-year picker | required. Rendered as `Oct2026`. |
| **Name** | Text, ≤ 80 characters | required. Underscores are not allowed (they separate the parts); leading and trailing spaces are trimmed. |

- **Live preview**: the form shows the generated name as you type ("Project name: `Wasl_Campaign_Oct2026_JGE Launch`").
- **Storage**: `Project.name` holds the composed string, so lists, search, sorting, CSV and Delivery Pulse all keep working. The parts are stored as well: `Project.naming = { brand, type, month: "2026-10", title }`. `Project.brand` stays in sync with `naming.brand`.
- **Uniqueness**: no two active projects may have the same composed name (case-insensitive; 409 with a clear message).
- **Existing projects** (497 imported) keep their names. Editing one shows the four fields **pre-filled**: brand from the assigned brand, type and month detected from the old name where possible (e.g. "June 2025 | Program | Wasl | 360 Social" gives Program / Jun2025). The user confirms, and saving renames it to the new format. Projects without `naming` show a small "Legacy name" badge.
- **Validation**: brand, type, month and name are required on create, through the API and the UI. The Excel import accepts either the four columns or a full name. With the four columns, the name is composed; with only a name, it's kept as legacy, with a warning.
- **Search and filters**: the Projects list gets **Type** and **Month** filters, alongside Brand.
- **Short code**: unchanged (it's entered separately), but it's suggested from the brand and type, e.g. `WASLC`.

## Part B: Pearity tag integration (Utility is the source of truth)

### Concept

- **Tag mapping**: every Utility task can have **exactly one Pearity tag**, a one-to-one mapping for the whole organisation. Any number of users can generate content against that same tag, which is one-to-many for usage.
- **Generate button**: clicking **Generate** on a task opens Pearity's **production engine**, with task ID, brand, category and tag already filled in. Nobody types anything.
  - The first click on a task creates the tag. Every later click, by anyone, reuses it.
- **Pearity dashboard**: the Pearity team builds a dashboard that reads a **Utility API** to list each user's tasks, together with their tag (or "not generated yet" and a Generate action).

### Data (in Utility)

**`PearityTag`**
- `task` (unique; one tag per task)
- `tagId`: stable, e.g. `pt_7k3m9q2x`, random and URL-safe
- `tagName`: generated as `Brand_Category_TaskCode`, e.g. `Ajmal_Design_GenAIHub-65`. Spaces and unsafe characters become `-`. Brand and category fall back to `NoBrand` / `General`.
- `createdBy`, `createdAt`
- `brandSnapshot`, `categorySnapshot`

The `tagName` never changes once created, even if the task is renamed, so the Pearity side stays stable.

**`PearityTagUsage`**: `tag`, `user`, `source` (`utility` | `pearity`), `at`. It records who generated against the tag and when (one-to-many).

### Settings → Integrations → Pearity (admin)

- **Enabled** on/off. The Generate button is hidden when it's off.
- **Production engine URL template**, with placeholders, e.g. `https://app.pearity.ai/production/new?tagId={tagId}&tag={tagName}&taskId={taskId}&taskCode={taskCode}&brand={brand}&category={category}&project={project}`. Values are URL-encoded, and the template is validated as `https://`.
- **API keys** for the Pearity server: **create** (the key is shown once), **list** (name, prefix, last used, created by), and **revoke**. Only a hash is stored. Keys are scoped to `pearity:read` and `pearity:tags`.
- An optional **allowed IPs** list for API calls.

### In Utility (UI)

- **Generate**: a **Generate** button in the task detail sheet header and in the task table's ⋮ menu, shown to anyone who can view the task.
  - **No tag yet**: a small confirm ("This creates the Pearity tag `Ajmal_Design_GenAIHub-65` for this task") → create the tag → open the production engine in a new tab.
  - **Tag exists**: open the production engine directly with the existing tag ("Using existing tag …").
  - Either way, a usage entry is recorded and a task history entry `pearity_generated` is written.
- **Tag display**:
  - The task detail shows a **Pearity tag** chip (copyable, links to the engine), plus a "Generated by" list (avatars, times).
  - The tasks table gets an optional **Pearity tag** column, and a filter **Has tag / No tag**.

### Utility API for Pearity (server-to-server)

- **Base path**: `/api/integrations/pearity/v1`, with the header `Authorization: Bearer <api key>`.
- **User identity**: the Pearity user is identified by `email` (users must use the same email in both systems). An unknown or inactive email gets 404.
- **Rate limit**: 600 requests per minute per key. All responses are JSON and every call is audited.

| Method | Path | Purpose |
|---|---|---|
| GET | `/tasks?email=&status=open\|all&updatedSince=&limit=&cursor=` | The user's assigned tasks: `{ taskId, taskCode, title, status, dueDate, actualStartAt, actualEndAt, project {id, name, code}, brand {id, name}, category {id, name}, utilityUrl, pearityTag: {tagId, tagName, createdAt, createdBy} \| null, generateUrl }`. Cursor-paginated. |
| GET | `/tasks/:taskId?email=` | A single task (the email must be allowed to view it) |
| POST | `/tasks/:taskId/tag` | Body `{ email }`. **Idempotent**: returns the existing tag, or creates it. Returns `{ created: boolean, tag, generateUrl }` and records usage with source `pearity`. |
| GET | `/tags/:tagId` | Looks up a tag and returns its task, so Pearity can resolve a tag back to Utility |
| GET | `/tags?updatedSince=` | Bulk sync of all tags (for Pearity's own cache) |

- **Concurrency**: creating a tag is atomic (unique index on `task`), so two simultaneous Generate clicks return the same tag.
- **`generateUrl`**: the production-engine URL template filled in for that task.
- **Documentation**: `docs/pearity-integration.md` is written for the Pearity team. It covers auth, every endpoint with examples (curl), error codes, the tag-naming rules, and a suggested design for the "Utility dashboard" inside Pearity (task list with brand, category, tag, and Generate / Open tag).

### Security

- **API keys**: hashed (SHA-256 with a prefix), revocable, never logged, and compared in constant time.
- **Scoping**: key requests can only read data for the given email's visible tasks, applying the same rules as the UI.
- **Data returned**: task title, codes, brand, category and dates. **No** comments, files, people's personal data, or anything else.
- **Logging**: an activity log entry for key create and revoke and for tag create.

## Done when

- Both type checks and the build pass.
- **Part A**:
  - Creating a project requires the four fields and saves the composed name.
  - Duplicates are rejected.
  - Editing a legacy project pre-fills the fields.
  - Filters work.
  - The Excel import handles both forms.
- **Part B**:
  - Generate creates the tag once, and later clicks (including by another user) reuse it.
  - The engine URL is built from the template.
  - The API works with a key and is rejected without one, with a revoked key, or with a wrong email.
  - Pagination works, and idempotent tag creation holds under concurrent calls.
  - The documentation file exists.
- **Browser**: the project form, the Generate flow (the engine URL opens; it can point at a placeholder until the real URL is known), and the settings page.
